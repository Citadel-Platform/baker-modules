# Working in this codebase

This application was generated by Citadel's Factory. `baker.lock.json` records
which module versions it was built from; read it before assuming where
something came from.

What follows is what the generated code assumes. It is not a style guide for
the whole world — it is what this codebase already does, so that a change made
here reads like the code around it.

## What Baker owns and what you own

Baker wrote the first commit and nothing after it. There is no manifest to
regenerate from and no upgrade path: **editing generated files is expected and
correct.** `baker verify` will tell you a module has moved on in the catalogue;
it will not offer to move your code, and you should not treat its output as a
task list.

If you want a newer module's code, read what changed and apply it by hand. The
lock is provenance, not a contract.

## The rules the generated code follows

**No invented data.** Nothing here contains made-up customers, orders, metrics
or activity. The records screen is empty and says why it is empty. This is not
an oversight to be helpfully filled in — an application demonstrated with fake
data is one somebody eventually demonstrates by accident, in front of the
client whose data it is pretending to be. There is a widget test asserting the
empty state; if you find yourself deleting it, stop.

**"Not configured" is a state, not an error.** A build with no platform address
and a build whose platform is unreachable look identical from a failed request,
and only one of them is anybody's fault. `PlatformClient.isConfigured`,
`UnconfiguredIdentity` and `NoCapture.isRecording` each exist so a screen can
say which. Do not collapse them into a generic failure.

**Failures read as sentences.** `ApiFailure` carries a title, a message and a
remedy. Never render an exception's `toString` into the interface: that is how
a client ends up reading a stack frame. Every new failure surface goes through
`ApiFailure`.

**The platform address is compile-time.** `--dart-define=CITADEL_PLATFORM_API_BASE_URL`.
It is not a runtime setting because an application that can be pointed at a
different platform by editing a preference can be pointed at somebody else's.

**Design tokens, not literals.** Spacing, colour and type come from
`AppTokens`. A colour written twice is a colour that will one day be two
colours. The tokens deliberately match the Citadel console's, so this
application and the console it is administered from age together.

## The seams, and why they are empty

Three things ship as interfaces with a deliberately inert default:

- **`Identity`** — sign-in. A bootstrap cannot know which provider a client
  uses. The default is `UnconfiguredIdentity`, which is not "signed out": an
  application with no sign-in wired has nowhere to sign in to, and rendering
  "signed out" sends somebody looking for a login screen that does not exist.
- **`Capture`** — telemetry. The default records nothing and says so. Whether a
  client's application starts sending telemetry somewhere is a decision with a
  privacy answer attached, and not one a bootstrap should have made.
- **`PlatformClient`** — the Citadel Platform API. Unset until the build says
  otherwise.

Filling one in is ordinary work. Making it *look* filled in — a no-op that
reports success — is the thing to avoid: an application whose telemetry is
switched off and one whose telemetry is broken already look the same from
inside, and `isRecording` is the only thing that tells them apart.

## Layout

```
lib/
  main.dart              the entry point, and nothing else
  src/
    app.dart             the MaterialApp and its theme
    shell.dart           navigation and the screens
    design/              tokens and primitives — the design system module
    api/                 the Platform API client and its failures
    auth/                the identity seam
    telemetry/           the capture seam
test/                    widget tests, including the empty-state guard
```

Screens live in `shell.dart` until there are enough of them to warrant a
directory. Two destinations is not enough.

## Before you finish

```
flutter analyze
flutter test
```

Both are expected to pass on a clean generated tree. If they do not, that is a
defect in the module, not something to work around locally — say so, and it
gets fixed in `baker-modules` where the next client also gets the fix.
